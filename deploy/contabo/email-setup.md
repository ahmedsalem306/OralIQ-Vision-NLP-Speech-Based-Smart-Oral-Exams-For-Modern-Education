# Transactional email setup for oralliq.com

The owner created a Resend account and verified `auth.oralliq.com` on November 14,
2026. The supplied key was transferred privately and configured in the candidate
server's mode-0600 environment file. SMTP authentication succeeded with TLS 1.3
both from the host and inside the API container; application mail configuration is active.
No key value is stored in this runbook or git. The existing application supports SMTP;
no new vendor SDK is required.

The owner explicitly approved one test message to their Gmail address. The application's
mailer sent it and SMTP accepted it. The owner confirmed that it arrived in **Inbox**.
Recipient authentication-header checks still need separate confirmation. No signup flow or
password-reset delivery is established by this transport test.

1. Owner signs into [Resend](https://resend.com/signup). Start with the free tier for
   pilot testing; its 100-email daily cap cannot cover 500 same-day new registrations.
   Recheck current [quotas/pricing](https://resend.com/pricing) before a school launch.
2. Add `auth.oralliq.com` as a sending domain. Copy **the exact records generated by
   Resend** into GoDaddy and verify the domain. Do not invent DKIM/SPF values or replace
   unrelated MX records. Leave open/click tracking off for verification/reset messages.
3. Create an API key limited to sending for that domain. Treat it as the SMTP password;
   do not put it into chat, a screenshot, git, a command argument or frontend environment.
   Place it through the agreed secure server configuration process.
4. Only after verification/key setup, apply these values in the private server `.env`:

```dotenv
EMAIL_BACKEND=smtp
SMTP_HOST=smtp.resend.com
SMTP_PORT=465
SMTP_SECURITY=ssl
SMTP_USERNAME=resend
SMTP_PASSWORD=<private sending key>
SMTP_FROM=OralIQ <noreply@auth.oralliq.com>
```

Keep `FRONTEND_URL` on the actual active frontend origin so confirmation/reset links
work; switch it to `https://oralliq.com` only when that frontend domain is connected.
Recreate the API/worker containers after editing environment configuration; restarting
the existing container alone does not load changed Compose environment values.

Then explicitly authorize a real delivery test to the owner's address, check inbox/
spam, verify DKIM/SPF results, and exercise signup and password reset end to end.
Do not declare email ready merely because an SMTP connection or authentication succeeds.

References: [SMTP settings](https://resend.com/docs/send-with-smtp),
[verified domains](https://resend.com/docs/dashboard/domains/introduction).

## Quota and delivery behavior before rollout

The current backend sends verification mail synchronously; it has no durable email
outbox, automatic delivery retry or operator quota alert. A 202 response acknowledges
the request without revealing whether the address exists. API and UI text now say
the request was received instead of claiming that a message was sent. SMTP acceptance
would not prove inbox delivery either. Per-account resend throttling remains in place.

Google login verifies the Google account's email through its signed identity token and
does not send a site verification email. It can reduce transactional email demand for
a pilot. Users who need password signup still need a working email provider/quota.

Before a high-volume launch, provision adequate quota and implement/test bounded email
queuing/retries, expiry handling, abuse controls and operator delivery/quota monitoring.
A paid plan removes its daily cap; it does not remove provider burst-rate restrictions.
These requirements remain open; the wording correction is not an email queue.
